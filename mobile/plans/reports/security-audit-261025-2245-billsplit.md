# Security Audit Report

**Project:** BillSplit Auto (PRM course project — Flutter mobile app + .NET 9 ASP.NET Core backend)
**Scope:** `backend/` (.NET 9 Clean Architecture: Domain/Application/Infrastructure/Api) and `mobile/` (Flutter 3.44.6 / Dart 3.12.2). Excluded: `.git/`, `node_modules/`, `build/`, `.dart_tool/`, `bin/`, `obj/`, `android/.gradle/`.
**Mode:** Comprehensive audit (default — no `--red-team`, no `--fix`, report-only)
**Files checked:** 27 backend `.cs` files (excluding `bin/`/`obj/`) + 22 mobile `.dart` files, plus manifests (`*.csproj`, `pubspec.yaml`), `appsettings*.json`, `launchSettings.json`, `billsplit.db` (schema + row counts), and git tracking state.

## Findings

| 1 | High | Secret / A02 Crypto Failures | `backend/BillSplit.Api/Program.cs:31`, `backend/BillSplit.Infrastructure/Services/TokenService.cs:22` | Hardcoded fallback JWT signing secret `"BillSplitSuperSecretKeyForPrmMobileAppProject2026!"` is duplicated in two files and used whenever `Jwt:Secret` is absent from config. Neither `appsettings.json` nor `appsettings.Development.json` sets `Jwt:Secret`, so **this hardcoded string is the actual signing key in every environment today**, including if `ASPNETCORE_ENVIRONMENT=Production` were set, since `launchSettings.json` only has Development profiles and nothing in `Program.cs` forces a real secret in production. Anyone who reads the source (every teammate, grader, or future repo visitor) can forge a valid JWT for any `userId`/phone/email and impersonate any user. | Move the secret to configuration only (user secrets locally, environment variable or secret manager in any deployed environment). Remove the hardcoded fallback string entirely; instead, throw a startup exception if `Jwt:Secret` is missing so the app fails safe. Rotate to a new secret (randomly generated, ≥32 bytes) once removed — the current value must be treated as permanently compromised since it is public in source. |
| 2 | Medium | `.env` exposure / Secrets hygiene | Repo root, `backend/`, `mobile/` (no `.gitignore` present anywhere) | No `.gitignore` file exists at the repo root or inside `backend/`/`mobile/`. `git status` shows `backend/` and `mobile/` as entirely untracked (`?? backend/`, `?? mobile/`) — nothing has been committed yet beyond the initial empty commit. This means `backend/BillSplit.Api/appsettings.json`, `appsettings.Development.json`, and the SQLite file `backend/BillSplit.Api/billsplit.db` are all currently un-ignored and would be committed as-is on the next `git add`/`git commit`. The `.db` file is a build artifact that regenerates itself (`EnsureCreatedAsync()` + `SeedDefaultBanksAsync()` in `Program.cs`) and should never be tracked. | Add a `.gitignore` (root, or backend-specific) before the first commit that includes `backend/**/bin/`, `backend/**/obj/`, `*.db`, `*.db-shm`, `*.db-wal`, `appsettings.Development.json` (or at minimum `appsettings.*.local.json`), and standard .NET/Flutter ignores. Currently `appsettings.json`/`appsettings.Development.json` contain no secrets (verified — only `Logging`/`AllowedHosts` keys), so this is about preventing future accidental commits of real connection strings or a future real `Jwt:Secret` value, and about not bloating the repo with a regenerable binary DB file. |
| 3 | High | STRIDE: Information Disclosure / OWASP A01 Broken Access Control | `backend/BillSplit.Infrastructure/Services/FriendService.cs:19-71`, `backend/BillSplit.Api/Controllers/FriendsController.cs:35-45` | `POST /api/friends/add` lets any authenticated user submit an arbitrary phone number and, if a match exists, immediately receives that user's `BankBin`, `BankAccountNo`, and `BankAccountName` in the response — with the friendship auto-set to `Accepted` with no consent from the target user (`FriendService.cs:50`, code comment admits this is a demo shortcut: "Tự động chấp nhận trong demo để trải nghiệm nhanh"). Since Vietnamese phone numbers follow a small, well-known format (`RegisterRequestDto` regex `^(0[3\|5\|7\|8\|9])+([0-9]{8})$`), an attacker with one valid account can enumerate the ~10^8 phone number space (or target known numbers) to harvest other users' real bank account numbers and names without their consent, and silently become their "friend" in the process. | Require the target user to explicitly accept the friend request before any profile/bank data is shared (set initial `Status = FriendshipStatus.Pending` and only expose bank fields to the requester after `Status == Accepted`). Add rate limiting on `POST /api/friends/add` to blunt phone-number enumeration regardless. Consider returning a generic "request sent" response without echoing the target's bank details until acceptance. |
| 4 | High | STRIDE: Spoofing / OWASP A04 Insecure Design | `backend/BillSplit.Infrastructure/Services/DebtService.cs:174-232` (`AutoSettleByMessageAsync`), `backend/BillSplit.Api/Controllers/DebtsController.cs:55-65` | `POST /api/debts/auto-settle` trusts a client-submitted free-text string (`request.RawBankMessage`) as proof of payment. The server only regex-matches a `BSxxxxx` debt code inside that string and marks the matching debt `Paid` — it never verifies the amount in the message against `debt.Amount`, never checks the message came from a real bank notification (no OS-level/Play-Integrity/notification-source attestation is passed through), and never calls any bank API to confirm the transfer actually happened. Any text containing a valid `BSxxxxx` code is accepted. The endpoint is scoped to the creditor's own JWT (`d.CreditorId == creditorId`), so a *debtor* cannot call this directly to settle someone else's debt on their own account — but the creditor's own client (or anyone who captures/replays the creditor's JWT, or a modified APK on the creditor's device) can submit a fabricated "bank message" for a partial or zero real payment and have the debt marked fully Paid. This is the core business-logic trust boundary named in the task brief, and today it is unguarded. | Do not trust client-submitted notification text as the sole proof of payment. At minimum, validate the amount embedded in `RawBankMessage` (via `UniversalBankParser`) matches `debt.Amount` before auto-settling, and reject partial/mismatched amounts. For real security (beyond a course project), the only reliable fix is a server-side bank webhook/API integration (e.g., VietQR's actual bank notification webhook, or a bank's own transaction API) rather than parsing arbitrary client-reported text. Short of that, clearly document to users/graders that `auto-settle` is a convenience feature, not a payment-verification mechanism, and keep `manual-settle` (explicit creditor confirmation) as the trustworthy path. |
| 5 | Medium | STRIDE: Tampering / OWASP A01 Broken Access Control | `backend/BillSplit.Infrastructure/Services/DebtService.cs:43-54` (`SplitExpenseAsync`) | `SplitExpenseAsync` accepts a client-supplied `request.GroupId` (`Guid?`) and assigns it directly to the new `Expense.GroupId` with no check that the calling `creditorId` is actually a member of that group (compare with `GroupService.GetGroupDetailAsync`, which correctly filters by `g.Members.Any(m => m.UserId == currentUserId)`). Today there is no endpoint that lists expenses by `GroupId`, so this cannot yet leak another group's data to an outsider — but it is a latent IDOR: the moment a "group expense history" endpoint is added (a natural next feature), any authenticated user could tag their own expense onto any other group's ID, polluting that group's expense/debt history. | Before assigning `request.GroupId`, verify the caller is a member of that group (same pattern used in `GroupService`), and reject the request with 403/400 if not. Add this check now so it isn't missed when a group-expense-listing feature is added later. |
| 6 | Medium | STRIDE: Denial of Service / OWASP A07 Auth Failures | `backend/BillSplit.Api/Controllers/AuthController.cs`, `Program.cs` (no rate limiter registered anywhere) | No rate limiting exists on `/api/auth/login` or `/api/auth/register` (confirmed: no `AddRateLimiter`/`UseRateLimiter` calls anywhere in the backend). Combined with BCrypt's deliberately slow hashing this isn't catastrophic, but login is open to unthrottled credential-stuffing / brute-force attempts, and register is open to account-creation spam. | Add ASP.NET Core's built-in rate limiting middleware (`Microsoft.AspNetCore.RateLimiting`, included in .NET 9) with a fixed-window or token-bucket policy applied to `/api/auth/*` at minimum. |
| 7 | Low | STRIDE: Information Disclosure / OWASP A05 Security Misconfiguration | `backend/BillSplit.Api/Program.cs:117-121`, `backend/BillSplit.Api/Properties/launchSettings.json` | Swagger/OpenAPI UI is gated behind `app.Environment.IsDevelopment()`, which is correct — but both `launchSettings.json` profiles (`http`, `https`) hardcode `ASPNETCORE_ENVIRONMENT=Development`, and there is no documented production profile at all. If this project is ever deployed without explicitly overriding that variable, Swagger (with the "try it out" execution UI) stays enabled, as does the permissive `AllowAll` CORS policy described in finding #8, since neither is gated by environment in `Program.cs`. For a course project this is low risk (unlikely to be deployed publicly), but worth checking before any demo/deployment outside localhost. | When/if deploying beyond local demo, add a `Production` launch profile (or rely on hosting-platform env vars) with `ASPNETCORE_ENVIRONMENT=Production`, and double check Swagger stays off. |
| 8 | Low | STRIDE: Tampering / OWASP A05 Security Misconfiguration | `backend/BillSplit.Api/Program.cs:58-66` | CORS policy `"AllowAll"` permits any origin, any method, any header (`AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader()`), and is applied unconditionally regardless of environment. For a mobile-only client (Dio from a Flutter app, not a browser) CORS has limited practical impact since CORS only constrains browser-based callers, but it does mean any website could issue authenticated-looking fetches from a victim's browser if a browser-based client were ever added, or if Swagger UI is used from a browser against a non-localhost deployment. | Scope CORS to the specific origins actually needed (e.g., the Swagger UI origin in dev, and any future web client's exact origin), rather than `AllowAnyOrigin`. For a pure mobile-app backend, CORS can be tightened to almost nothing. |
| 9 | Low | Code pattern: Insecure randomness (informational risk) | `backend/BillSplit.Infrastructure/Services/DebtService.cs:255-261` (`GenerateDebtCode`), `backend/BillSplit.Infrastructure/Services/GroupService.cs:173-178` (`GenerateInviteCode`) | Both debt codes (`BSxxxxx`, 5 chars from a 32-char alphabet ≈ 1.6M combinations, scoped per-creditor via `DebtCode` uniqueness) and group invite codes (6 chars from the same 32-char alphabet ≈ 1.07B combinations, globally unique) are generated with `new Random()`, which is not cryptographically secure and is seeded from the system clock. Debt codes are a payment-matching identifier, not an authorization secret (the auto-settle lookup is additionally scoped by `CreditorId == creditorId`, so guessing a code alone doesn't let a stranger settle someone else's debt — finding #4 already covers the deeper trust issue there). Group invite codes are more sensitive: anyone who learns or predicts a 6-character invite code can join that group and see its members' names/phone numbers (`GroupMemberDto`). `Random()`'s predictability is a much weaker concern here than the small output space combined with no expiry — a determined attacker could brute-force a live invite code via the public-shaped `POST /api/groups/join` endpoint since there's no rate limiting (see finding #6) and no attempt-count lockout. | Switch both generators to `System.Security.Cryptography.RandomNumberGenerator` (or `Random.Shared` is still not CSPRNG — use `RandomNumberGenerator.GetInt32`). More importantly for invite codes, add rate limiting to `/api/groups/join` and consider an expiry/regeneration option for invite codes since they are the actual access-control gate for group membership. |
| 10 | Low | OWASP A07 Auth Failures (password policy) | `backend/BillSplit.Application/DTOs/AuthAndBankDtos.cs:15-17` | `RegisterRequestDto.Password` only requires `[MinLength(6)]` with no complexity rule. Low priority for a course demo but easy to fix alongside the rate-limiting change. |

| 13 | Info | STRIDE: Repudiation (non-issue, verified) | `backend/BillSplit.Infrastructure/Services/DebtService.cs:208-211, 247-249` | Debt settlement does record `SettlementType` (`Auto`/`Manual`), `PaidAt` timestamp, and for auto-settlement the raw bank message text (`debt.BankRawMessage = request.RawBankMessage`) is persisted. ## Verified Non-Issues

- **SQL Injection:** All data access goes through EF Core LINQ (`_context.Users.FirstOrDefaultAsync(...)`, etc.) with no raw SQL or string concatenation anywhere in `BillSplit.Infrastructure`. Mobile `sqflite` calls (`local_storage_service.dart`) use parameterized `where`/`whereArgs`. No injection vector found.
- **XSS / WebView:** No `WebView` usage found anywhere in the Flutter codebase (`grep` for notification listener / webview turned up nothing); not applicable to this native Flutter UI.
- **Unsafe deserialization / `eval`:** No `eval`, `Function()`, `pickle`/`yaml.load`/`BinaryFormatter`, or similar dangerous deserialization calls found in either stack.
- **OCR data exfiltration:** `bill_scan_assign_page.dart` and `bill_ocr_parser.dart` confirmed fully local — `google_mlkit_text_recognition`'s `TextRecognizer.processImage` runs on-device, and `BillOcrParser.parse` is a pure string-processing function with zero network calls. No image or extracted text is sent anywhere.
- **VietQR / CRC16 implementation:** `crc16.dart` and `vietqr_encoder.dart` implement the standard CRC-16/CCITT-FALSE algorithm and EMVCo TLV structure correctly for QR payload integrity checking. This is appropriately *not* treated as a security credential — it is a checksum for payload correctness, not an authentication mechanism, and `Random()`/non-crypto generation is irrelevant here since no randomness is used in this file at all.
- **Group role elevation (Owner vs Member):** The `GroupRole` enum (Owner/Member) exists in the schema, but no endpoint currently performs any owner-only action (no remove-member, delete-group, or promote/demote endpoints exist yet in `GroupsController`). There is nothing to bypass today; flagged here only so it's checked again once such endpoints are added.
- **Database file contents:** `backend/BillSplit.Api/billsplit.db` was inspected directly (SQLite). `Users`, `Expenses`, `GroupMembers`, `Debts`, `Friendships`, and `Groups` tables are all empty (0 rows). Only the `Banks` table is populated (36 rows of public bank reference data: BINs, names, logo URLs) via `SeedDefaultBanksAsync()`. No real user PII is currently present in the tracked/untracked DB file.
- **Mobile notification-listener auto-settle wiring:** The task brief describes an "auto-detects incoming payments... auto-settle debts" flow via `NotificationListenerService`. Searching the mobile codebase found `UniversalBankParser` is implemented but **not called from anywhere else in `lib/`**, no `android/` platform directory exists yet in this worktree, no notification-listener permission or plugin is wired up, and no mobile code calls the backend's `/api/debts/auto-settle` endpoint. The feature is partially built (backend endpoint + parsing heuristic exist) but not yet connected end-to-end on the mobile side, which reduces real-world exploitability of finding #4 today — it will matter once the missing wiring is added.

## Methodology Notes

- Stack detection confirmed via `backend/*.csproj` (net9.0, EF Core 9.*, BCrypt.Net-Next 4.2.0, JwtBearer 9.*, Swashbuckle 6.6.2) and `mobile/pubspec.yaml` (Flutter SDK `^3.12.2`, flutter_bloc 9.1.1, dio 5.11.1, sqflite 2.4.5, flutter_secure_storage 11.2.0, google_mlkit_text_recognition 0.15.0, image_picker 1.2.4).
- `.env` exposure check: no `.env*` files exist in either stack. No `.gitignore` exists anywhere in the repo (root/backend/mobile) — see finding #2.
- Secret scanning: ran structured regex sweeps for AWS/GitHub/Stripe/Slack/Google/Anthropic key formats, private key headers, and generic password/token/secret assignment patterns across `*.cs`/`*.json`/`*.dart`/`*.yaml`/`*.xml`. Only the hardcoded JWT fallback (finding #1) was found; no other credentials, API keys, or connection strings with embedded secrets were found.
- Dependency audit: `dotnet list package --vulnerable --include-transitive` run against `BillSplit.sln` (all 4 projects) — 0 vulnerable packages. `flutter pub outdated` run for Dart — no CVE scanner exists for the Dart ecosystem (noted limitation), version currency checked instead.
- STRIDE analysis focused on the Debts/Friends/Groups trust boundaries as instructed, with particular attention to the auto-settle-via-notification-text business logic (finding #4) and IDOR risk across Debts/Friends/Groups endpoints (findings #3, #5; Groups and Debts list/detail queries were otherwise found to correctly scope by current user).
- No files were modified. No credentials found were executed or used. This is a report-only comprehensive audit; `--fix` was not requested and was not applied.

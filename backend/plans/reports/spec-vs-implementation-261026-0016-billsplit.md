## Module-by-module detail

### Module 1 — Auth
Backend matches the spec's request/response shape closely: `POST /api/auth/register` and `POST /api/auth/login` exist in `backend/BillSplit.Api/Controllers/AuthController.cs`, validate via `ModelState`, and return `AuthResponseDto { Token, User }`. The spec's response also includes a `refreshToken` field that `AuthResponseDto` (`backend/BillSplit.Application/DTOs/AuthAndBankDtos.cs:57-61`) does not have — there is no refresh-token mechanism anywhere in the codebase. On the mobile side, `AuthBloc` (`mobile/lib/features/auth/presentation/bloc/auth_bloc.dart`) calls `/auth/login` and `/auth/register` correctly and persists the JWT via `flutter_secure_storage`. However, `_onAuthCheckRequested` (line 86) calls `dioClient.dio.get('/users/profile')` to validate the stored token on app start — this endpoint does not exist on the backend at all (confirmed: no `UsersController` exists), so every app restart with a stored token will get a 404/exception and fall through to `Unauthenticated()`, silently logging the user out. This is a real, concrete bug, not just a missing feature.

### Module 2 — Profile & avatar upload
Entirely missing on both sides. There is no `UsersController.cs` anywhere in `backend/BillSplit.Api/Controllers/`, no `IUserService`/`UserService`, and no DTOs for profile update or avatar upload in `AuthAndBankDtos.cs` or `AppDtos.cs`. `UserDto` exists but is only used as part of `AuthResponseDto`. On mobile, `pubspec.yaml` has no `image_cropper` dependency (only `image_picker: ^1.2.4`, used solely for OCR bill scanning), and there is no profile-edit page or route in `main.dart`'s `GoRouter` (only `/login`, `/register`, `/home`, `/split`, `/qr-payment`, `/friends`, `/groups`). To implement this would require: a new `UsersController.cs` + `IUserService`/`UserService.cs` + `UpdateProfileRequestDto`/multipart avatar-upload action (likely using `IFormFile` and static file serving), plus a new mobile `profile_page.dart` with `image_picker` + `image_cropper` wired to `POST /api/users/avatar`.

### Module 3 — Bank directory
Backend: `BankService.SeedDefaultBanksAsync()` (`backend/BillSplit.Infrastructure/Services/BankService.cs:36-47`) seeds a static hardcoded list of 31 banks/e-wallets (`GetComprehensiveBankList()`) once at startup if the table is empty. There is no `VietQrSyncBackgroundService`, no `IHostedService` registration in `Program.cs`, no call to `api.vietqr.io`, and no `IMemoryCache` usage anywhere in the backend. `GET /api/banks` (`BanksController.cs`) just returns whatever is in the DB. Mobile: `register_page.dart` calls `dioClient.dio.get('/banks')` live and passes the result into `BankPickerBottomSheet`, which does real-time local search — but this is a live network call on every register-page open, not a cache. `LocalStorageService` (`mobile/lib/core/storage/local_storage_service.dart:43-50`) does create the `bank_cache` SQLite table exactly per spec schema, but there is no insert/query method for it anywhere in `local_storage_service.dart`, and no code path populates or reads it. The spec's "cache-first, sync on first open" behavior is not implemented; it's a straight live fetch every time.

### Module 4 — Friends & net balance
Backend: `GET /api/friends` and `POST /api/friends/add` exist (`FriendsController.cs`), plus the already-verified `GET /api/friends/pending` and `POST /api/friends/{id}/accept`. There is no `GET /api/friends/{friendId}/debts` endpoint from the spec. More importantly, `FriendService.GetFriendsWithNetBalanceAsync` was not read in full detail this session for its net-balance math, but `IFriendService`'s only balance-bearing field is `FriendDto.NetBalance` — the net balance calculation (sum of debts as creditor minus sum as debtor between the two specific users) needs verification; the committed `DebtService.GetNetBalanceSummaryAsync` only computes a *global* net balance across all counterparties, not per-friend. Mobile: `friends_page.dart` is confirmed 100% local mock (`_friends` hardcoded list, `_showAddFriendDialog` just does `setState` with fabricated data) — no Dio import, no API call whatsoever, despite `AuthBloc` and other pages already having the Dio pattern available to copy.

### Module 5 — Group management
Backend: `POST /api/groups`, `GET /api/groups`, `GET /api/groups/{id}`, `POST /api/groups/join` all exist and work (`GroupsController.cs` + `GroupService.cs`), with correct invite-code generation and membership-scoped queries (`GetGroupDetailAsync` filters by `g.Members.Any(m => m.UserId == currentUserId)`). Contract drift from spec: `CreateGroupRequestDto` is `(string Name, string Category, string? AvatarUrl)` — there is no `memberIds` array; the spec's example of inviting members at group creation is not supported. Members can only join afterward via `POST /api/groups/join` with the invite code. Mobile: `groups_page.dart` is confirmed fully local mock (`_groups` hardcoded list; "create group" and "join group" dialogs only do `setState` and show a `SnackBar`); no Dio call to any of the four working backend endpoints.

### Module 6 — Notification listener
This is the one area where the ground truth has changed since the last audit: an `android/` platform directory now exists in this worktree (it did not before). However, inspecting `android/app/src/main/kotlin/com/billsplit/mobile/MainActivity.kt` shows it is the unmodified Flutter scaffold stub (`class MainActivity : FlutterActivity()`, 5 lines, no overrides). `AndroidManifest.xml` only declares `CAMERA` permission and the standard launcher activity/intent-filter — there is no `<service>` entry for a `NotificationListenerService`, no `BIND_NOTIFICATION_LISTENER_SERVICE` permission, and no Kotlin/Java source file implementing `onNotificationPosted`. No `MethodChannel` registration exists in `MainActivity.kt` or anywhere in `lib/`. `UniversalBankParser` (`mobile/lib/core/utils/universal_bank_parser.dart`) is a well-implemented pure-Dart class matching the spec's regex/keyword logic almost exactly, but a repo-wide search found zero call sites for `UniversalBankParser.parse` outside its own file — it is dead code from the app's perspective. To implement this module would require: a new `NotificationListenerKt.kt` service class + manifest `<service>`/permission entries + a `MethodChannel("com.billsplit.app/notification")` bridge in `MainActivity.kt`, plus Dart-side code in `main.dart` or a new service class to listen on that channel and feed `UniversalBankParser.parse(...)` results into `LocalStorageService.insertPendingTransaction(...)`.

### Module 7 — Smart bill split
Backend is solid: `POST /api/debts/split` (`DebtsController.cs` + `DebtService.SplitExpenseAsync`) validates title/amount/sum-of-splits, creates an `Expense` + N `Debt` rows with server-generated unique `BSxxxxx` codes, and returns `DebtDetailDto` list — this matches the spec's contract shape closely (field names differ slightly: response wraps debts under `{message, debts}` rather than `{expenseId, totalAmount, debts}`, but the core data is equivalent). Mobile is the real gap: `SplitBillPage` (`mobile/lib/features/split/presentation/pages/split_bill_page.dart`) implements the full hybrid shared-pool/personal-item split UI and OCR bill-scan-assign flow, but `_onSavePressed` (lines 363-416) never imports or calls Dio — it generates a `debtCode` with a local `Random()` (lines 389-392) and immediately navigates to `/qr-payment` with client-fabricated data. No `POST /api/debts/split` call exists anywhere in `lib/`. This means the entire split-bill feature, however polished the UI, never persists an `Expense` or `Debt` row on the backend — the QR code shown afterward references a debt code the server has never heard of, so Module 9's auto-settle (which looks up debts by `DebtCode` + `CreditorId`) could never match it in practice.

### Module 8 — VietQR EMVCo TLV generator
Fully implemented and wired, no gaps found. `mobile/lib/core/utils/vietqr_encoder.dart` and `crc16.dart` implement the EMVCo TLV structure (tags 00/01/38/53/54/58/62/63) and CRC-16/CCITT-FALSE checksum correctly per the spec (previously confirmed in the security audit's "Verified Non-Issues" section). `QrPaymentPage` calls `VietQrEncoder.encode(...)` with the logged-in user's real `bankBin`/`bankAccountNo` pulled from `AuthBloc`'s `Authenticated` state, and renders it with `qr_flutter`. This is a genuinely complete, correctly offline-functioning module — the one module that most exceeds "partial."

### Module 9 — Auto-settle + manual settle
Backend `POST /api/debts/auto-settle` and `POST /api/debts/{id}/manual-settle` both exist and work (verified this session via live curl testing per the task brief). Contract drift from spec: the spec's request body is `{debtCode, receivedAmount, rawMessage}` (pre-parsed amount and debt code supplied by the mobile client); the actual implementation is `AutoSettleRequestDto(string RawBankMessage, string? BankShortName)` — the server does its own regex extraction of both the debt code (`BS[A-Za-z0-9]{4,6}`) and the amount (`ExtractAmount` helper) from the raw text, rather than trusting client-parsed fields. This is actually a better security posture than the spec describes (client can't just assert a `receivedAmount`), and was the subject of this session's already-verified fix. The gap is end-to-end wiring: nothing in `lib/` ever calls `/api/debts/auto-settle` (no notification listener exists per Module 6, so there is no trigger), and manual settle is also unwired — `QrPaymentPage._onManualSettlePressed` (`qr_payment_page.dart:72-104`) only shows a confirmation dialog and a `SnackBar`, then navigates home; it never calls `POST /api/debts/{debtId}/manual-settle`. It also structurally couldn't today, since `QrPaymentPage` is only ever given a `debtCode` string (not the `Guid debtId` the endpoint requires), and since Module 7 never creates a real debt in the first place.

### Module 10 — Dashboard / statistics
Missing on both sides. No `StatisticsController.cs` exists in `backend/BillSplit.Api/Controllers/`, no `IStatisticsService`, and no DTOs resembling `spendingByCategory`/`monthlyTrend` anywhere in `AppDtos.cs` or `AuthAndBankDtos.cs` — `GET /api/statistics/dashboard` does not exist. `fl_chart: ^1.3.0` is present in `pubspec.yaml` but a repo-wide search for `fl_chart`, `PieChart`, or `BarChart` imports/usage in `mobile/lib/` returned zero matches — it is an unused dependency. `home_page.dart` renders the "financial overview" card with literal hardcoded strings (`'+450.000 đ'`, `'600.000 đ'`, `'150.000 đ'` — see lines 95-103, 130, 165 of `home_page.dart`), not even reading from `DebtService.GetNetBalanceSummaryAsync` (which does exist and is a reasonable backend building block for this, via `GET /api/debts/summary`). There is also no `/dashboard` or `/statistics` route registered in `main.dart`'s `GoRouter`.

## Recommended next features

Given the above, in priority order for closing the gap to spec within course scope:

1. **Wire Module 7 end-to-end** (highest value, currently the biggest functional hole): make `SplitBillPage._onSavePressed` call `POST /api/debts/split` via Dio instead of fabricating a local debt code, and pass the real server-returned `debtId`/`debtCode` into `QrPaymentPage`. Everything downstream (Module 9's settle flow, Module 10's real statistics) depends on real debts existing.
2. **Wire manual-settle** in `QrPaymentPage._onManualSettlePressed` to call `POST /api/debts/{debtId}/manual-settle` — this is a small, self-contained fix once a real `debtId` is available from fix #1, and gives a working settle path even without the notification listener.
3. **Fix the `GET /users/profile` 404-on-launch bug** in `AuthBloc._onAuthCheckRequested` — either add a minimal `UsersController.GetProfile` endpoint (also needed for Module 2) or change the check to a local-only token-presence check.
4. **Wire Modules 4/5 (Friends/Groups) to real endpoints** — the backend already has working, tested endpoints for both; this is "only" a mobile Dio-wiring task (replace the hardcoded lists with `FutureBuilder`/state calls to `GET /api/friends`, `POST /api/friends/add`, `GET /api/groups`, `POST /api/groups`, `POST /api/groups/join`), no new backend work required beyond possibly adding `GET /api/friends/{friendId}/debts`.
5. **Build Module 10 (Dashboard/statistics)** — add a small `StatisticsController` + `IStatisticsService` on top of existing `Debt`/`Expense` data (category sums, monthly trend), then wire `fl_chart`'s `PieChart`/`BarChart` into a real dashboard screen or into `home_page.dart`, replacing the hardcoded numbers.
6. **Module 2 (Profile/avatar)** — add `UsersController` with `GET/PUT /api/users/profile` and `POST /api/users/avatar` (local disk storage + static file serving is sufficient for course scope; no need for cloud blob storage), plus a mobile profile screen with `image_picker` + `image_cropper`.
7. **Module 6 (native notification listener)** — this is the most Android-platform-heavy piece (Kotlin `NotificationListenerService`, manifest permissions, `MethodChannel`), but the Dart-side parsing logic (`UniversalBankParser`) and SQLite storage (`pending_transactions` table) are already done and tested in isolation, so it is mostly "wiring," not net-new logic design.

**Optional/lower priority for course scope** (explicitly spec'd but reasonable to skip or stub for a PRM course project):
- `VietQrSyncBackgroundService` (Module 3's 24h background sync against `api.vietqr.io`): a static seed of 31 banks already covers the realistic bank-picker use case for a demo; a live background sync adds operational complexity (hosted service, external API dependency, retry/cache invalidation) with little grading value. Document the static list as an intentional simplification rather than building the sync job.
- FCM push notifications (mentioned in the Module 9 sequence diagram, "Backend → FCM Push Notify"): requires a Firebase project, device token registration flow, and server-side FCM SDK integration. For course scope, an in-app refresh/poll or local notification on settle is sufficient; FCM is a reasonable cut.
- SQLite `bank_cache` read/write path (Module 3 mobile): the table schema already exists; actually using it (vs. the current live-fetch-every-time approach) is a nice-to-have for offline resilience, not essential for grading a course demo.
